Why don't these four records agree?

A production agent at Teem, built on top of the billing pipeline I had already rebuilt. When a billing exception reached Finance, Claude read the signed agreement, the ticket and the HubSpot, Stripe and Deel records, and explained why they disagreed. Money stayed in code, and autonomy was earned in stages.

01 · The business problem

The rebuilt billing pipeline cut Finance's weekly queue from 60–80 tickets to 2–3 exceptions. Those exceptions were the hard ones. Resolving one could mean opening a signed agreement, a HubSpot deal, a Stripe subscription and a Deel record, then working out which one was wrong.

The arithmetic was never the slow part. Understanding why four systems told four different stories was. That is reading work: contract clauses, ticket history, effective dates written in prose. It is also exactly the kind of work where a confident wrong answer moves money.

A rate on the ticket that did not match the agreement. A placement active in Deel with no live item in Stripe. A contracted fee missing from the invoice. Two active agreements for the same client and no rule for which one governed. A customer whose identity did not resolve cleanly across HubSpot and Stripe. Each one meant opening several systems, reading a contract and deciding which record was right.

02 · Why not let the model fix it?

Interpreting a contract is one permission. Changing a financial record is another. I designed the workflow so the first never implied the second.

Deterministic code · Python / JavaScript
Owns the money
Fees, prorations, credits, effective dates and authorization are computed in code. Same input, same output. The model never produces a number that gets written to Stripe.
Agent · Claude with tool calling
Owns the interpretation
Gathers evidence through tool calls, reads clauses and records, and returns structured findings that explain the discrepancy and cite where each claim came from.
03 · Architecture
Exception reaches Finance→Claude + tool calls→Structured findings→Independent review, isolated context→Deterministic policy→Execute · Finance in Teams · Block→Revalidate, then write→Read-back reconciliation→Audit record

Reasoning, validation, evaluation, authorization and execution are separate steps with separate owners. A second model call, with its own isolated context, reviews each recommendation. Then a deterministic policy, not the model, decides what happens: execute, send to Finance for approval through a Microsoft Teams Adaptive Card, or block.

04 · What the agent reads

Everything a person on Finance would open to understand an exception, and nothing that writes.

Exception ticket
The request, its history and the reason the billing pipeline stopped it.
Signed agreement
The contract clauses the billing is supposed to reflect.
HubSpot
The deal, quote and line items recorded for the client.
Stripe
The live subscription, items, prices and billing history.
Deel
The workforce contract behind each placement.

Claude classified each case as underbilling, overbilling, missing fee, incorrect proration, contract-to-billing mismatch, duplicate billing, effective-date mismatch, ambiguous customer identity, multiple active agreements, or no action required. Every recommendation named a target, an effective date, a risk level and the evidence it relied on, and an action without provenance was never eligible for automatic execution. Text inside contracts, tickets, CRM notes and API responses was handled as data, so nothing written in a document could change the policy or trigger a financial tool.

05 · Autonomy, in stages

Autonomy was something the agent earned with evidence, one stage at a time.

July 2026
Finance approves everything
Every financial write needed Finance approval in Microsoft Teams. The agent investigated and proposed; a person decided.
August 2026
Shadow evaluation
The independent evaluator ran in shadow mode, recording verdicts against Finance's real decisions without affecting execution.
Late August 2026
Limited autonomy
A deterministic policy gate began allowing automatic execution for a small allowlist of known low-risk actions, only when validation and the independent evaluation both passed.
The authorization tiers I built in late August
Tier 0 · read-only
Querying systems, retrieving agreements and tickets, comparing states, classifying and explaining. No approval needed.
Tier 1 · no financial effect
Opening a Finance exception, adding a CRM note, updating investigation status, sending a Teams notification, attaching evidence or asking for missing information.
Tier 2 · automatic financial writes
Only for a small allowlist of actions that were known, verifiable by deterministic code, limited in impact, reversible where possible, covered by evaluation cases and checked by post-write reconciliation.

Finance kept large credits, retroactive changes, full cancellations, new kinds of remediation, policy exceptions, incomplete evidence, any disagreement between the agent and the evaluator, and anything outside the allowlist. A missing signed agreement, an unresolved customer identity or an unexpected state in Stripe blocked execution entirely, though the agent could still investigate.

Finance's decisions were kept as regression evaluation cases, so every later change to a prompt, a formula or the policy had to agree with what Finance had already decided. The model was not fine-tuned on them. The release gates weighted errors asymmetrically: a wrong PASS can move money, while an unnecessary review only costs some automation, so the gates treated the first as far more serious.

06 · Guardrails

The checks that sit between a good-sounding answer and a changed invoice.

Approval bound to the payload
Each approval is tied to a hash of the exact action. An approval for one change cannot authorize a different change later.
Confidence can only lower autonomy
A less confident model sends more cases to Finance. A more confident model never sends fewer.
Revalidate before every write
State and idempotency keys are checked again immediately before execution, in case anything moved while a case waited.
Read-back reconciliation
A case closes only after the system reads Stripe back and confirms the result matches what was approved.
Independent reviewer
A second model call with an isolated context reviews each recommendation, so the reviewer is not persuaded by the first answer.
Audit record
Evidence, model and prompt versions, the policy decision and the approver are stored for every case.
