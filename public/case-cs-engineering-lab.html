Personal lab · synthetic data FastAPI · Flagsmith · Docker · kind · GitHub Actions

A checkout service where shipping the code and turning it on are separate steps

I built this lab to practice the technical side of Customer Success Engineering. A FastAPI checkout service gets its new flow from Flagsmith, an open-source feature-flag platform, through the official Python SDK. One container image runs as a Development instance and a Production instance, so the code ships once and a flag decides who sees the new checkout.

Around that service I tested what happens when Flagsmith fails, ran everything in Docker Compose and on a local Kubernetes cluster, wrote 170 automated tests in five tiers, logged 12 failures I found while building, and wrote Customer Success exercises against fictional accounts.

Read this first. This is a personal lab with synthetic data. It has no real customers and no commercial results, and it is not affiliated with Flagsmith. Every figure on this page is a lab test result, measured on my machine or on a CI runner. "Development" and "Production" are the names of two lab instances. The code lives in a private repository.

01 · Deployment and release

The same code, on in one instance and off in the other

Flagsmith runs self-hosted from upstream's Compose file, pinned at version 2.290.0. On each checkout, the service asks it whether the new flow is on for that customer. Development and Production are two instances of the same image, each with its own environment key, and a script sets up the flag configuration through Flagsmith's admin API.

With identical code deployed to both, the live Flagsmith tests show the feature on in Development and off in Production, and the segment and override values reach the right test personas.

A segment rule

Customers whose plan is beta form a segment, and the segment gets the new flow.

An identity override

One pilot customer is switched on through an override on its own identity.

An off switch

Turning the flag off takes effect with no restart of the service, and a live Flagsmith test checks it.

02 · Failure handling

When Flagsmith fails, checkout serves a safe default within a known time

A flag lookup sits in the checkout request, so a slow or broken flag service becomes a slow or broken checkout unless the failure is bounded. New features fail closed. When a lookup fails, the feature stays off for that request.

An overall deadline per lookup

2s socket timeout, 2.5s in total

Socket timeouts do not cover DNS. During an outage, DNS resolution took 3 to 8 seconds outside any socket timeout, so each lookup also has a 2.5-second overall deadline.

SDK retries removed

a bounded wait for a failed lookup

The SDK's default retries turned a 2-second timeout into more than 8 seconds. I set them to zero so a failed lookup costs a bounded amount of time. This bounds failure time, and I did not design a retry strategy.

Readiness without Flagsmith

a flag outage keeps checkout in service

The readiness check does not depend on Flagsmith, so an outage of the flag service cannot take checkout out of rotation. Liveness and readiness are separate endpoints.

Every default leaves a trace

logs and named diagnostics

A default flag handler and a catch around unexpected SDK errors serve the default, and each default served writes a log line. Diagnostics name a rejected key, a wrong endpoint or an incompatible API.

The contract tests run the real SDK against a local HTTP server whose behavior the test controls. Connection refused, a slow server, slow DNS, 401 and 403, 500, an HTML page and JSON with the wrong schema all end the same way, with a default served and no 500 on checkout.

03 · Containers and local Kubernetes

Rollouts under constant traffic on a one-node local cluster

The service builds from a Dockerfile on python:3.12-slim, runs as a non-root user and declares a health check. A Docker Compose stack runs Flagsmith, PostgreSQL and two app instances, and the Compose tests cause real Flagsmith outages against it.

I then deployed it to kind, a tool that runs a Kubernetes cluster inside Docker on one machine, with kubectl and Kustomize, using a shared base and one overlay per lab instance. Each instance gets its own namespace, Deployment and Service, and its environment key comes from a Secret. The Deployment has readiness and liveness probes, a preStop hook, and a rolling update that adds one pod at a time and keeps every existing pod serving until its replacement is ready (maxSurge 1, maxUnavailable 0).

05 · Findings

Twelve failures, each written down with raw output before the fix

I kept the raw output of every failure before fixing it, and tested hypotheses with dedicated measurements of latency during rollouts, cold workers and DNS timing inside pods. Eleven of the twelve findings are fixed. Five of the fixed ones follow.

A rollout reported success and dropped connections

Kubernetes marked the rolling update as successful while connections were being dropped. It stopped once a sleep was added to the preStop hook.

A 200 with the wrong schema escaped the SDK

A response with status 200 and the wrong JSON shape got past the SDK's own handling. Wrong-schema JSON became a contract test case, and it serves a default.

DNS outlasted the socket timeout

Name resolution during an outage ran past the socket timeout, which led to the 2.5-second overall deadline on each lookup.

A false "unhealthy"

A health check reported the service as unhealthy when it was working.

A port problem only Linux showed

An IPv6 port problem appeared only on the Linux CI runner, and CI caught it first. Another finding appeared only during slow DNS on Windows.

Finding 7 · open

One fallback in 213 requests, seen once

In one run, a single request out of 213 got the default instead of the flag value. I have seen it once. I measured four explanations, and each one was refuted, so the finding stays open in the log together with what I ruled out.

My guess is CPU contention. I have no measurement that confirms it, and I have not fixed this finding.

06 · The console

A console that names each failure and the next step in plain language

The console is server-rendered with Jinja templates, plain CSS and JavaScript, and reuses the design system from my Career Agent project. It has five areas.

  • Overview
  • Feature releases by instance and by persona.
  • Diagnostics for connection, authentication, endpoint, readiness and liveness, each with a next step written in plain language.
  • Customer adoption on synthetic accounts, with the reasons behind each risk.
  • Playbooks

Environment keys stay on the server. The two instances compare each other, which is how the diagnostics catch a Development key used in the Production instance, a mistake the app cannot detect alone. The 58 interface tests cover the console at four widths, with axe scans in the light and dark themes.

08 · What this does not prove

The limits of a lab

It has no customers. There is no revenue, adoption or retention result here. The accounts, personas and adoption data are synthetic, and every number on this page comes from a lab test.

Kubernetes ran on one local node. The cluster was kind on my machine and on a CI runner, with one node, no high availability and no load testing. Timings were measured on one machine and one runner, and the runner is fresh and unloaded.

Parts of Flagsmith stayed untested. I did not test local evaluation, percentage rollouts, the Edge Proxy, the Helm chart or Flagsmith upgrades, and I have not used Flagsmith in a job.

Failure handling bounds time. I removed the SDK's retries to cap how long a failed lookup takes. I did not design a retry strategy.

Accessibility was checked by automated tests. Axe scans and keyboard tests ran; nobody checked the console with assistive technology or with real users. The console has no login and is for local use.

One finding is open. Finding 7 has no confirmed cause and no fix.

My customer-facing experience comes from elsewhere. I worked with real customers at Profectum, a process-automation consultancy in Fortaleza, Brazil, that implemented Pipefy for its clients, and at Pipefy, a Brazilian SaaS for workflow automation used by finance, legal, HR and operations teams at large companies.
