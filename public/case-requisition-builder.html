Case study 04
Sixth release, in production HubSpot · Fountain ATS · Deel · Airtable · n8n · Netlify

A requisition was a manual workflow. I turned it into a record.

Not a form that got faster. A hiring process that stopped living in people's memory: naming conventions, access settings and workflow choices that each operator had to remember became validation, and copy and paste between three systems became data flow.

01 · Before

One requisition meant repeating the same operational process from scratch

A Success Manager had to leave the onboarding ticket, open other systems, locate or create supporting records, reproduce information the CRM already held, configure the opening, assign the recruiter, set access permissions, choose the correct workflow, and then return to HubSpot to document what had happened. For every single requisition. The internal training guide spends roughly eight pages getting from we need to hire someone to a usable opening.

As is. Four configuration screens, repeated in full for every role.
Source gathering
Find the client and onboarding information in the CRM
Collect Success Manager, recruiter, website, call recordings, compensation, responsibilities, qualifications, schedule and notes
Carry all of it by hand into the next system
Position and location
Search for the role; if the position does not exist, request its creation from the Talent Acquisition Director and wait
Create the location: client name plus interview date, owner, remote flag, country, time zone, language
Opening and settings
Follow the naming convention from memory, set it active, select the recruiter
Paste the requisition details into a generic additional info field
Limit access on, sourcing opening off, then link the right workflow: requisition or replacement
Return to the CRM and record the outcome by hand

02 · After

HubSpot stopped being where the process started and became where the process is controlled

The Success Manager no longer builds the requisition across systems. She describes the hiring request once, from the onboarding record she already owns. The builder opens with twelve pieces of context already carried over from the ticket. After submit, the orchestration resolves identities, creates or reuses locations, creates the openings, assigns the recruiter, grants access, registers every opening for traceability, writes a note back into HubSpot, pins it to the ticket, advances the pipeline stage, and for Enterprise creates child tickets linked to the parent.

To be. One entry point, one submission, several openings.
03 · The interface

Multiple roles under one contract are tabs, not separate trips through the process. The form detects when a request spans several locations or entities and says so, because each requisition can carry its own interview date, recruiter and schedule.

Validation runs before execution, so an error is caught in the form rather than discovered downstream in the ATS.

05 · The second layer, Fountain to Deel

The builder was never an isolated automation. Once a candidate reaches the contract stage, a second workflow picks the thread up. The earlier process asked the operator to copy a Stripe ID out of the CRM and paste it into the ATS to avoid typos, which is the kind of instruction that tells you exactly where the system should be doing the work.

06 · The model broke before the code did

The first version assumed one deal equals one hiring cycle. Enterprise clients break that: a single contract and a single invoice can cover three roles that are operationally independent, with different interview dates, different interviewers, different start dates and sometimes different locations. One ticket could not represent that, and Finance had no signal telling them when each individual hire should start being billed. I evaluated custom objects, child records and custom properties before choosing, because the modelling decision was the actual problem. The orchestration was the easy part.

Parent and child, one invoice
Parent ticket · the contract, the billing anchor
Role A · own interview date, own start
Role B · own recruiter, own location
Role C · own start signal to Finance

The biggest change was not that the form became faster. The business process stopped living in people's memory.

Rules became validation.
Copy and paste became data flow.
Repeated setup became orchestration.
And the CRM became the place where the whole hiring request can be started, tracked and understood.
08 · How it was built
Front end, no build step
~5,100 lines of JavaScript: a central state container with subscription based rendering, crosstab coordination between windows, cancellable requests with timeouts, retry with growing waits, and DOM rendering protected against injected content.
Orchestration
A 49 step n8n orchestration: webhook entry points with controlled responses, per item and whole batch code execution, persistent data tables as memory across runs, structured logging, explicit failure termination, and a dedicated micro workflow for the recruiter list.
Rollout
Unblock manually first, automate once the process settles. Netlify with server side rewrites and continuous deployment from Git. Documentation and training so a non engineer can own it.
