Which accounts deserve a human's attention today?

An internal Revenue Operations agent for a synthetic portfolio of DTC ecommerce brands. Deterministic Python and SQL signals shortlist the accounts first; Claude then investigates each one through constrained, read-only tools and produces source-backed recommendations that a person approves.

Role
Sole designer and engineer
Data
30 synthetic DTC brands
Output
At most 3 recommendations per run
Validation
305 automated tests, 14 scenario cases
01 · The business problem

A Revenue Operations team looking after dozens of ecommerce brands cannot read every dashboard every morning. Most days, most accounts are fine. The useful question is narrower: which accounts deserve a human's attention today, what changed, and what would a reasonable next step be?

The case is built on a synthetic portfolio of 30 direct-to-consumer brands with the signals a retention and lifecycle team actually watches: abandoned carts, lapsed customers, campaign performance, attribution and data freshness. The data is invented; the constraints are the ones a real team would impose.

02 · Why not just an LLM?

Handing 30 accounts of raw metrics to a model and asking what matters would be cheap to build and impossible to trust. So the work is split by what each side is good at.

Deterministic signal engine · Python / SQL
Owns the facts
Metrics such as ROAS, data freshness and reconciliation, time windows, thresholds, the shortlist ranking and the confidence score are computed in code. Same input, same output, every run. The model never calculates a number it later cites.
Agent · Claude with tool calling
Owns the interpretation
For each shortlisted account, the agent decides what to look at, pulls context through narrow tools, weighs conflicting signals and writes a recommendation that cites where every claim came from.
03 · Architecture
30 accounts→Python / SQL signals→Deterministic top-8 shortlist→Claude + read-only tools→Publication gate→Human approval→≤ 3 recommendations

The shortlist is bounded before the model is involved, so model cost and attention scale with the number of accounts worth discussing, not with the size of the portfolio. Tool, cost and iteration budgets, plus a cap on output tokens, limit how much the agent can spend before it must conclude.

04 · Tool contract

The agent sees five tools. Four read context; one proposes an action. None of them writes to a system of record.

get_account_context
Profile and baseline for one account, so the agent can tell a real change from normal behaviour.
get_campaign_performance
Lifecycle and campaign results for the account over the analysis window.
get_commerce_context
Commerce signals such as carts, orders and revenue context behind a flagged change.
get_recent_account_activity
Recent activity on the account, so a recommendation does not repeat something already in motion.
propose_crm_task
Drafts a follow-up task as a proposal. It returns a structured suggestion for a person to approve; it does not create anything.
05 · Guardrails

Every recommendation passes through checks that fail closed. If any of them fails, the recommendation is not published, and the rejection is recorded with its reason.

Data freshness
Stale inputs block expansion recommendations instead of producing a confident answer about last month.
Reconciliation
A reconciliation exception in the deterministic layer blocks expansion recommendations.
Source references
Every claim must cite a source reference issued in the same run.
Schema & shortlist
Output that does not match the recommendation schema, or names an account outside the shortlist, is rejected without silent repair.
Budgets
Tool, cost and iteration budgets and output-token caps keep the loop bounded. Confidence is derived in code from observed conditions.
No write tools · human approval
The agent can only propose. A person decides what reaches a CRM.
06 · Evaluations

Two kinds of test, kept apart on purpose. Automated tests and scenario cases check the deterministic layer, the gates and the agent's handling of prepared situations. Live Claude canaries run against the real model, and their results are kept distinct from the automated ones so neither can flatter the other.

07 · Failure log

Kept in public because the failures say more about the engineering than the passes do.

Deterministic layer
An off-by-one in the 30-day window
The lookback window counted one day wrong. It lived in signal code, not in a prompt, which is exactly why facts belong in code: it could be found, fixed and tested like any other bug.
Evaluation harness
An evaluator that passed empty output
An evaluation check returned a pass for a run that produced no output. I corrected the evaluator's contract so an empty result can no longer count as a pass.
Publication gate
A gate that rejected valid references
The gate rejected source references that the system itself had issued. I corrected the reference contract and kept the gate fail-closed, so anything it cannot verify is still rejected.

09 · Observability & scaling
Per run
What gets recorded
Each run writes a receipt to a SQLite ledger with the model, tokens, estimated cost, run latency, tool arguments and rejections, so a recommendation can be traced back to what produced it.
Prompt caching
Cached and measured
Tool definitions and system prompts are cached, and cache reads are logged alongside token cost and latency.
Account Radar
A read-only operator console
An operator can review what the agent produced without any path to write to a business system.
Storage
Optional PostgreSQL layer
Parity checks compare the SQL results with the Python computation of the same metrics.
As the portfolio grows
What scales, and what does not
The deterministic scan grows with the number of accounts. The model's work stays bounded by the shortlist and the recommendation cap.
10 · Production extension
Adapters built, read-only
Production integration path
Read-only adapters for HubSpot, Shopify and Klaviyo exist, with Slack and Healthchecks monitoring. None of them writes to a business system, and a person still approves every proposed task. n8n scheduling, Metabase dashboards and an MCP server exposing the same read-only tools are design intent and have not been built.
